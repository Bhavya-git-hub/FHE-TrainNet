# Faculty demonstration script

A 5-10 minute walkthrough. Everything runs live; nothing is pre-recorded.

**Before they arrive**

```bash
cd FHE_TrainNet
.venv\Scripts\activate                      # Windows
python scripts/probe_library.py             # ~10 s, generates the capability table
streamlit run app/dashboard/Home.py
```

Open the **Faculty Demo** page and leave it ready. First encrypted run pays 20-35 s
of key generation; press **Run the full demonstration** once beforehand so the
context is cached for the session.

---

## 0. The question (30 seconds, no slides)

> A hospital wants a model trained on patient records. The cloud provider that
> has the compute must not see the records. Homomorphic encryption lets the
> provider compute on ciphertexts - but every multiplication burns through a
> finite budget, and restoring that budget is the most expensive operation there
> is. So: **when should you spend it?** That is what this project measures.

## 1. Overview page (1 minute)

Point at two things only.

- **The configuration table** — the dataset, the model, the CKKS parameters, and
  the line that matters: *"chain provides 10 levels; one training step costs 5;
  2 steps fit between refreshes."* That ratio is the whole problem in one line.
- **The capability table on the right** — generated by probing the library, not
  copied from documentation. Note the four `NO` rows: `scale`, `level`,
  `noise_budget`, `bootstrap`.

> Say this out loud, because an examiner will ask: **SEAL does not implement CKKS
> bootstrapping.** This system never claims otherwise. What restores capacity here
> is a client-aided refresh, labelled as such on every screen.

## 2. Encryption Lab (1 minute)

Press **Encrypt this record**.

- A real record goes in. Roughly 700 ms later it is about 2 MB of ciphertext - an
  expansion of some 60,000x on 32 bytes of features. That is the price of privacy.
- The decrypted column comes back agreeing to about 26 bits, *not* exactly. **CKKS
  is approximate arithmetic.** Everything downstream inherits that.

  (Read the numbers off the screen rather than from this page - they move with the
  CKKS parameters in the sidebar, which is itself worth pointing out.)

## 3. Computation Lab (1 minute)

Leave `x * y + x` selected, press **Compute on ciphertexts**.

- 4.500028 comes out against an exact 4.5 - about 17 bits of agreement - computed
  without ever decrypting `x` or `y`.
- Then point at the cost table: **the multiplication consumed a level.** Switch the
  operation to `x + y` and re-run to show addition costs nothing.

> This is the crux: additions are free, multiplications are not, and training is
> made of multiplications.

## 4. Faculty Demo page - the main event (3-4 minutes)

Press **Run the full demonstration** and narrate as it goes.

Stages 1-3 replay what they have just seen, quickly. Then:

**Stage 4, training.** Two runs of the identical workload.

- *Fixed policy first.* Watch the **Levels** metric: it goes 10→5, refreshes,
  10→5, refreshes - every single step. It never touches the lower half of its
  budget.
- *Adaptive second.* Watch it go 10→5→**0**, then refresh. It continues when 5
  levels remain because it knows the next step needs exactly 5.

Read one CONTINUE reason aloud from the green box:

> *"5 levels remain and the next step needs 5; the ciphertext is within its
> operating range."*

**Stage 5, the capacity chart.** This is the picture to linger on. The fixed policy
is a flat line at 5. The adaptive policy is a sawtooth reaching 0. Same work, half
the refreshes.

**Stage 6, the comparison.** On the shipped configuration: **5 refreshes against
11, about 34% faster, identical accuracy (0.900 both).**

**Stage 7, the decryption.** The weights appear for the first time. They were
ciphertexts for the entire run; only the key holder can do this.

## 5. The honest part (1 minute)

Do not skip this - it is what makes the rest credible.

Open **Bootstrapping Monitor** and read the amber banner:

> *"Every event below is a client-aided refresh, not CKKS bootstrapping... its
> security consequence is that the owner sees the intermediate weights."*

Then open **Capacity Monitor** and point at the green box:

> *"Derived level count agrees with measured ciphertext size at every reading."*

Explain in one sentence: the level count is our own arithmetic, so it is checked
against a quantity the library actually produces - the serialized ciphertext size,
which sheds 174 kB per level at these parameters. If they ever disagreed, the page would say so.

## 6. Answering "but is adaptive actually better?" (1 minute)

The honest answer, and the strongest one:

```bash
python scripts/run_all_demos.py --demo 7
```

This sweeps the fixed interval and shows the tuning cliff:

- too long → the run **FAILS** on capacity exhaustion;
- too short → it **wastes** refreshes;
- exactly one value is optimal, and it must be found by tuning;
- **the adaptive policy was given no interval at all.**

> The claim is not that adaptive beats every possible fixed schedule. A perfectly
> tuned fixed interval ties it. The claim is that the right interval changes with
> the activation degree, the feature count and the modulus chain - and adaptive
> finds it every time without being told.

To make that concrete live: change **Polynomial activation** in the sidebar from
`sigmoid_deg3` to `sigmoid_deg5` and watch the sidebar's depth budget recompute.
The fixed interval that was correct a moment ago now is not.

## Questions they will ask

**"Is this real encryption or a simulation?"**
Real. TenSEAL over Microsoft SEAL, CKKS. `scripts/probe_library.py` calls each
operation and records the result; `docs/LIBRARY_CAPABILITIES.md` is its output. The
compute zone is given a context with no secret key, and a test asserts that
decryption from it raises.

**"So you didn't implement bootstrapping."**
Correct, and SEAL does not provide it. Faking it was the one thing the brief
forbade. The controller, the metric and the decisions are all real; the primitive
is a client-aided refresh and is labelled that way everywhere. `docs/LIMITATIONS.md`
section 1 sets out exactly what that does and does not invalidate, and
`docs/OPENFHE_BACKEND.md` covers the route to real `EvalBootstrap`.

**"Where is the noise measurement?"**
There is not one, because SEAL exposes no CKKS noise budget - see the four `NO`
rows on the overview. What is measured is level, ciphertext size and canary
precision, each tagged with its provenance. Inventing a "noise percentage" was
explicitly ruled out.

**"Why such a small model?"**
Depth. A hidden layer roughly doubles the 5 levels a step already costs, against a
budget of 10. It would need refreshing *within* every step, and then there is
nothing left to compare between policies.

**"Why is the accuracy the same for all three modes?"**
Because it should be. All three run the identical algorithm with identical seeds;
the only difference is the arithmetic. That the encrypted runs match the plaintext
reference exactly (0.900) is evidence the implementation is correct - and
`test_encrypted_training_matches_the_plaintext_mirror` asserts the weights agree
to within CKKS's own precision.

**"What happens if you get the parameters wrong?"**
Two failure modes, both handled. Try `scale_bits: 21` in the sidebar - it is
refused, because at that scale `1.5 × 2.0` was measured returning `3.52` while
raising nothing. And raise the learning rate to 0.8: the polynomial activation
leaves its monotone range, the gradient inverts, and the run reports a divergence
warning rather than presenting the collapsed accuracy as a result.
